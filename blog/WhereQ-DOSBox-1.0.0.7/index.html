WhereQ-DOSBox 1.0.0.7: DOSBox, inside an APK

November 13, 2026 · 10 min read
Dazhi Zhang (Tony)

The browser was not enough​

There is a fast way to put DOS on a phone. You open a web page, the page loads a JavaScript build of DOSBox, and a C:\> prompt appears. It works. It is also a different animal from DOSBox.

An x86 emulator running as WebAssembly inside a browser tab has to do three things a native program never has to do: it has to live inside a page, it has to ask the browser for every pixel and every sound sample, and it has to live by the browser's rules while it does it. The picture is a canvas. The sound is an audio buffer you have to keep fed. The keyboard is a web page's problem. And nothing about the machine can be written down and read back, because the machine is not a machine — it is a tab.

I wanted the other thing: the DOSBox core itself, compiled natively, running as a library inside the app. 1.0.0.7 is the release where that stopped being a plan and became an APK.

What "native inside an APK" actually means​

Concretely: the APK carries, for each of three ABIs, one native library — libdosbox.so — and that library is the emulator. Not a wrapper around one, not a bridge to a server: the CPU cores, the DOS kernel, the hardware emulation, the shell, and the SDL2 back end are all inside it. SDL2 is linked statically, so the APK ships one native library per ABI and has no SDL2 dependency at run time.

The welcome screen and a mounted C: drive. The core in the middle is the real DOSBox, not a re-implementation of it.

The three ABIs are arm64-v8a (64-bit phones), armeabi-v7a (32-bit phones) and x86_64 — the last one is not a phone ABI at all; it is there because the SDK ships x86_64 system images and the verification rig runs on an emulator. The build is CMake and the NDK, against SDL2 2.30.0. The app layer around it is Kotlin and AndroidX, and it reaches the emulator over JNI. The keyboard types into DOSBox through the same SDL_PushEvent → mapper → KEYBOARD_AddKey path a physical keyboard uses, so there is no second input path to teach a game.

The part that was genuinely hard: the JIT​

DOSBox has a JIT. It is a recompiling core: instead of walking a program instruction by instruction, it translates blocks of x86 into machine code while the program runs. Upstream builds its x86 dynrec with a GCC plugin, which the NDK's clang cannot do — and Android forbids the other half of the trick as well, because the stock code cache is a malloc'd block that is later made executable with mprotect(PROT_EXEC), and a hardened device will refuse to make heap memory executable at all.

Both problems turned out to be solvable. The portable code generators — arm64, armv7, x86_64 — emit machine code into a buffer with no plugin involved, and on Android the cache is allocated as anonymous RWX memory from the start, the one JIT-style allocation an untrusted app is allowed to make; the mprotect block is compiled out, because the memory is already executable. That is why the JIT is compiled into libdosbox.so for all three Android ABIs.

The shipped configuration is core=auto: a program that stays in real mode runs on the interpreter, exactly as before, and the JIT never engages; a program that switches into protected mode hands over to the recompiling core at the first mode switch. That change landed in 1.0.0.6, and both paths were verified there on the emulator — STARFALL in real mode, Ultima VIII in protected mode.

What 1.0.0.7 shipped: the core, pickable in the app​

In 1.0.0.6 I wrote, in the documentation and in this repository: if the JIT code cache cannot be allocated, put core=normal in dosbox.conf as the fallback.

Then I tried to follow my own advice, and it does not work. dosbox.conf is regenerated from the shipped template on every boot — deliberately, so that a change to the template reaches phones that are already installed — which means a hand-edited file is overwritten at the next start. And the file lives in the app's private directory anyway, where no file manager can reach it. The escape hatch I had documented was not reachable. A handful of old DOS programs do misbehave on the recompiler, and I had given them no way out.

So 1.0.0.7 put the choice in the app. The Config button in the Files panel opens a dialog with the five cores DOSBox knows:

The CPU core, pickable in the app: Auto (the default), Normal, Dynamic, Simple, Prefetch. DOSBox chooses its core when it starts, so the app asks whether to restart.

auto is the default, normal is the fallback for the case the JIT code cache cannot be allocated, and dynamic, simple and prefetch are there because DOSBox has always had them and there was never a reason to hide them. The choice is stored and written into the generated configuration, so it survives a restart and an app update. One small dialog — and a promise in the documentation that is finally true.

The keyboard of that release​

The DOS picture is 4:3 and centred, so in landscape there are black bars down the left and right of it. The always-on keys moved into those bars and became two columns: the modifiers — Esc, Tab, Ctrl, Alt, Shift, Backspace — on the left, and File, Ent, Space and the four arrows on the right. The middle of the screen stayed a DOS screen.

STARFALL, the example bundle: the game in the middle, the keyboard pads in the bars on either side of it.

Two honest notes​

The size. The first announcement said the APK was about 5.3 MB. It is about 15.5 MB now, and I would rather explain that than let you find it out from the download. Two reasons, both on purpose: the native libraries are stored uncompressed in the APK, so Android can map them straight out of it instead of copying them to disk on every install, and the app layer is Kotlin with AndroidX, which adds roughly 4.5 MB of dex. The trade is a bigger download for a faster install.

The verification. Everything I have run has run on an emulator — API 37, x86_64. There is no real ARM64 run yet and no on-device benchmark. The desktop baseline, which builds the same core with the same feature set, measures about 127 million instructions per second for the interpreter on an x86_64 host, and the real-time pacing check shows the emulator using under 5 % of one core to run DOS at 1× — but the phone number is still missing, and the JIT's RWX code cache is the risk surface I would want measured on real hardware first.

Get it​

The release APK is signed with the release key of this repository, so a later version installs over it in place:

👉 github.com/whereq/whereq-dosbox — tag v1.0.0.7

downloads/whereq-dosbox-1.0.0.7.apk
sha256: 2e97f12f3901acbdc23f62395316df25aa51f4a081d941a950b2d7dfa36910a1

The file itself is in the repository's history, at its own tag: https://raw.githubusercontent.com/whereq/whereq-dosbox/v1.0.0.7/downloads/whereq-dosbox-1.0.0.7.apk. Releases from 1.0.0.9 on are on the releases page.

It runs on arm64-v8a, armeabi-v7a and x86_64 devices, Android 5.0 and newer, entirely offline, with no account and no tracking. The project is GPL-2.0, and the DOSBox core is embedded with its AUTHORS, ChangeLog, COPYING and per-file headers intact.

Again, this post is not the documentation. The documentation is the repository: the technical reference — the native build, the JIT and the W^X problem, the save-state machine — the user guide, and the interrupt map that says which interrupt answers which question. Please read those rather than take my word for it. The announcement is where this all started, the user guide and the interrupt map are on this site too, and WhereQ-DOSBox is where the project stands today.

Thank you, DOSBox​

None of this is possible without the DOSBox project.

DOSBox was written by the DOSBox Team — a volunteer crew who took an operating system from 1994 and made it runnable on every machine the world has produced since, including the ones that did not exist yet. They kept it alive for three decades and gave it away to anyone who wanted it. WhereQ-DOSBox is a thin layer on top of their work. The originality, the craft and the generosity are entirely theirs.

This port is built on Em-DOSBox, the Emscripten build of DOSBox r4305 by Boris Gjenero, which grew out of Ismail Khatib's first attempt to compile DOSBox with Emscripten, and rode on the Emscripten work of Alon Zakai. The SDL2 library by Sam Lantinga carries the window, the audio and the touch input.

DOSBox is a trademark of the DOSBox project; this port is not affiliated with or endorsed by the DOSBox team.
