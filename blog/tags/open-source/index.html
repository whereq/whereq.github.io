A library you cannot trust from a README​

A component library is easy to publish and easy to ignore.

The README shows a picture of a button. The demo page shows a page somebody built to look like the library, with the real component never loaded. The actual code sits in somebody's app, behind a build step, where you cannot see it — so the one thing you want to check, does this thing work when it is really installed?, is the one thing nobody checks.

That is the gap this page closes.

whereq.ca now has a live demo of @whereq/react — and a playground to try it in.

The WhereQ Lab is built from one shared React component library. It lives on npm as @whereq/react, and the Lab now runs it in full: open /react and the real components from the published package render in front of you — not a screenshot of one, and not a story about one.

WhereQ-DOSBox 1.0.0.15: a console-style gamepad for your thumb

November 20, 2026 · 12 min read
Dazhi Zhang (Tony)

One thumb was never going to be enough​

There is a moment in every DOS game played on a phone where the game stops being a game and becomes a dexterity test.

You are holding the phone in two hands, and the game wants three things at once: go left, fire, jump. The on-screen keyboard is a good way to type MOUNT C . and a bad way to play that. One thumb stays on the arrows; the other one has to leave them to find the letter B, and for a second — a second that a game with a timer does not give you — nobody is steering.

So you play the games you can finish with one thumb, and you do not play the others. A keyboard built for typing is a fine typewriter and a poor controller.

1.0.0.15 gives that keyboard a second face.

WhereQ-DOSBox interrupts: the map of every INT in the emulator

November 19, 2026 · 14 min read
Dazhi Zhang (Tony)

The one interface every DOS program agrees on​

Here is something I did not expect to care about, and then could not stop caring about.

A DOS game from 1987 does not know what a graphics card is. It does not know that a mouse exists, or that a keyboard has a buffer. It knows exactly one thing: it can ask the machine a question by pushing a number onto the stack and executing INT. INT 10h and the machine will put a character on the screen. INT 16h and the machine will hand over a keystroke. INT 33h and the machine will tell it where the mouse is and which buttons are down.

That is the whole contract. Every game from 1991 to 1994 is written against it, and it never changed.

I have been reading DOSBox's interrupt layer properly for this article, and it turns out to be one of the most carefully built parts of the emulator — and one of the parts this port has had to think about hardest, because a touch screen is not a mouse and a phone is not a PC.

So here is the map.

WhereQ-DOSBox 1.0.0.12: the save that outlives the app

November 17, 2026 · 9 min read
Dazhi Zhang (Tony)

A save state is the one thing the emulator exists for. It is the whole machine, frozen — the CPU, the DOS memory, the video memory, the open file handles, the timers — so that you can come back to the exact moment you left.

Until this release, that frozen machine lived inside the app's own private storage. Android deletes that storage the moment the app is uninstalled.

So it happens the boring way. The phone is full, or the app starts misbehaving, or you simply decide to reinstall it. You install the APK again, the game bundle is still sitting in the folder you picked, you press Play — and the game starts at the very beginning.

Ten hours of progress, gone. Not because the game was lost. Because the app was.

And a phone that falls in the river takes the app with it, and the app takes the saves with it.

The corridor you have already walked​

A DOS game does not have an autosave. Some of them have a save file of their own; most do not; the ones that do usually put it somewhere in the current directory and expect you to find your way back through a menu.

So you do what every DOS player did in 1996: you play for forty minutes, you die in a corridor you have already walked twice, and you walk it again. Same door, same guard, same room with the lever you forgot to pull. The game does not know how far you got. Nothing on the phone knows either.

1.0.0.8 is the release that changed that — not with a better save file, but with a different idea of what to save.

WhereQ-DOSBox 1.0.0.9: the keyboard becomes a handheld console

November 16, 2026 · 10 min read
Dazhi Zhang (Tony)

A DOS game asks for a keyboard. The phone does not have one.

Until this release the answer was two thin columns of keys standing in the black bars beside the DOS picture: the modifiers on one side, File, Ent, Space and the arrow keys on the other.

Two columns, one key each, the DOS picture in the middle. It typed. It was also nothing like the thing it was standing in for.

It typed. You could type a path, move a cursor, hold a key down while something else happened on the screen. It worked.

What it did not do was anything a thumb could do. A DOS game is played with the left thumb on the arrows and the right thumb on the keys, and every one of those keys was a long way from where a thumb expects to find it. The picture was 4:3, the phone was 20:9, and the difference between them was exactly the space the keys were trying to live in.
